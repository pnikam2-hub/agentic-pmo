# Scope — editable risk/dependency/KPI layer, external plan import, agents on imported plans

*Status: draft for review · Build line: `master` · Scope owner: Prashant*

Three things were agreed. This note turns them into a buildable scope, states what the
current code actually does, and lists the decisions needed before code is written.

---

## 0. The agreed outcomes, restated

1. **The risk register, dependencies, rules and KPIs become project-owned data** that a
   user can add to, modify and delete — seeded by the plan agent's pack, then editable —
   with the dependency set visible as a **map**.
2. **An existing plan can be brought in from Microsoft Project or Oracle Primavera**
   instead of being generated by the plan agent.
3. **Monitor and Alert agents run on an imported plan**, and the risk register,
   dependencies and KPIs are kept consistent with it.

## 1. What exists today (the three facts that shape the work)

Grounded in this tree at `29b3fa1`:

- **Risk register, KPI definitions and monitoring rules are not data.** They exist only as
  JSON files inside each domain pack (`backend/domain_packs/<pack>/risk_register.json`,
  `kpi_definitions.json`, `monitoring_rules.json`). `POST /api/packs/{id}/apply` writes a
  *summary* into `project_packs.snapshot` — counts plus the top 12 risks (`routers/packs.py:105`).
  Nothing can be edited per project, and applying a pack overwrites the previous attachment.
  There is no `risks`, `kpis` or `rules` table.
- **Dependencies are a JSON array on the task row**, `Task.dependencies = [task_id, …]`
  (`models.py:78`). No type (FS/SS/FF/SF), no lag, no external identity. The pack WBS uses
  string refs (`"dependencies": ["T001"]`) and **`apply` drops them entirely** — seeded
  tasks arrive with no links at all (`routers/packs.py:84`). Plan-generated tasks likewise
  get `dependencies: []`.
- **The Monitor agent does not read dependencies.** It renders every task as one text line
  (status, priority, estimated hours, due date, `[OVERDUE]`) and appends the pack's rules and
  KPI names as prose for the LLM to interpret (`agents/monitor_agent.py:20-37`). It reads no
  actual dates, no % complete, no baseline, no float, no links. Alert detects anomalies with
  three crude tests: overdue, `status == "blocked"`, and missing estimates
  (`agents/alert_agent.py:77-96`).

So today the product's intelligence is *advisory prose over a plan the system itself
generated*. Points 1–3 ask it to become *auditable computation over a plan the system did
not generate* — that is the real size of this change.

Also worth knowing: `Milestone` exists as a table (`models.py:86`) but has **no router** —
nothing can create one through the API. Zero-duration imported milestones therefore have
nowhere to land unless we add endpoints or keep them as tasks.

## 2. Workstream 1 — project-owned risk / dependency / KPI / rule layer

### 2.1 New tables

All four are first-class, cascade on project delete, and carry provenance so the UI and the
agents can tell pack-seeded from imported from agent-proposed from manual.

| Table | Key fields |
|-----------------|-----------------------------------------------------|
| `risks` | `project_id`, `ref` (R01…), `title`, `description`, `category`, `probability` (High/Medium/Low or 1–5), `impact`, `score` (derived), `status` (open/mitigating/closed/realised), `owner_role`, `owner_name`, `early_warning_signals`, `mitigation`, `contingency`, `related_task_ids` (JSON), `source` (pack/import/agent/manual), `source_ref`, `updated_at` |
| `project_dependencies` | `project_id`, `predecessor_task_id`, `successor_task_id`, `dep_type` (FS/SS/FF/SF), `lag_days`, `source`, `external_ref`, `notes`. Unique on (pred, succ, type) |
| `kpis` | `project_id`, `ref`, `name`, `description`, `unit`, `frequency`, `target_operator`, `target_value`, `formula` (text), `formula_spec` (JSON, see 4.2), `dimension`, `source`, `related_phase` |
| `monitoring_rules` | `project_id`, `ref`, `category`, `trigger_condition` (text, for the LLM), `predicate` (JSON, machine-evaluable), `severity`, `recommended_action`, `related_risk_refs`, `active` |

`project_packs` stops holding content: it keeps the pack id and `applied_at`, and gains
`seed_mode` (`tasks_only` / `content_only` / `both`). The snapshot column is kept for
historical rows and no longer read by the agents.

### 2.2 Migration of existing data

One Alembic revision (repo currently creates tables with `init_db()`; add Alembic in the same
change so future schema work stops being manual):

1. Create the four tables.
2. Backfill `project_dependencies` from every non-empty `Task.dependencies` array as `FS`,
   lag 0.
3. For projects with an attached pack, seed the four tables from the pack JSON
   (idempotent on `(project_id, source_ref)`).
4. `Task.dependencies` stays readable and is kept in sync by the API layer for one release
   so the Kanban and any seed scripts keep working, then is deprecated.

### 2.3 API

```
GET     /api/projects/{id}/risks           ?status=&category=&source=
POST    /api/projects/{id}/risks
PATCH   /api/projects/{id}/risks/{risk_id}
DELETE  /api/projects/{id}/risks/{risk_id}  (archive; hard=true to purge)
POST    /api/projects/{id}/risks/from-pack  {pack_id, replace:bool}
GET     /api/projects/{id}/risks/matrix      5x5 probability x impact counts

GET     /api/projects/{id}/dependencies      edges + node metadata
POST    /api/projects/{id}/dependencies      {pred, succ, dep_type, lag_days}
PATCH   /api/projects/{id}/dependencies/{dep_id}
DELETE  /api/projects/{id}/dependencies/{dep_id}
GET     /api/projects/{id}/dependencies/check   cycles, orphans, dangling refs
GET     /api/projects/{id}/schedule/critical-path

GET|POST|PATCH|DELETE /api/projects/{id}/kpis[/{kpi_id}]
GET|POST|PATCH|DELETE /api/projects/{id}/rules[/{rule_id}]
POST    /api/projects/{id}/rules/{rule_id}/test  dry-run predicate
```

Validation rules, enforced server-side, not just in the UI:

- Reject an edge that would create a **cycle** (return the cycle path, not just 400).
- Reject cross-project edges and self-links.
- Deleting a task deletes its edges (already the pattern; add the FK + cascade).
- `PATCH` on a pack-seeded row flips `source` to `manual` and keeps `source_ref`, so a later
  "re-seed from pack" can report what it would overwrite instead of silently clobbering edits.

### 2.4 UI

New project-detail tabs: **Risks · Dependencies · KPIs · Rules**. This is where most of the
work sits, and where the meeting's "add/modify/delete" actually lands:

- **Risks**: table with inline edit, a 5×5 heat map, filters, and a "seed from pack" action
  that previews the diff (new / changed / edited-here).
- **Dependencies**: two views of the same data. *Map*: layered DAG (topological levels, phases as horizontal bands), edges labelled with
  type and lag, critical path in a distinct colour, blocked/overdue nodes flagged, cycle
  attempts refused with the offending path highlighted. Implemented as inline SVG with a
  small layout function — no external diagramming library, so nothing new to host. *Table*:
  predecessor/successor, type, lag, edit and delete.
- **KPIs**: definition editor (name, unit, target, formula spec) plus current value and trend.
- **Rules**: condition, severity, action, an active toggle and a "test" button that shows
  whether it currently fires and on which tasks.

`packs.js` today is an inspector; it stays as the pack browser and gains "apply content to
this project" rather than being the only place risks are visible.

## 3. Workstream 2 — import from MS Project / Primavera

### 3.1 Formats, honestly

| Source | Format | Status |
|--------------|-------------------|----------------------------------------------|
| MS Project | **MSPDI XML** (`.xml`, File → Save As → XML) | Parse in Python; straightforward, documented schema |
| MS Project | `.mpp` (native binary) | **Not parseable in Python.** Needs MPXJ (Java) as a side converter, or the user exports XML. Do not promise `.mpp` upload until that bridge is decided |
| Primavera P6 | **XER** | Tab-delimited, block-structured (ERMHDR + %T/%F/%R tables). Parseable in Python; format is de-facto not official, so expect quirks per export |
| Primavera P6 | **P6 XML** | Parse in Python; more verbose than XER but better defined |
| Excel/CSV task list | — | Cheap fallback worth having (many "Primavera exports" arrive as Excel) |

Recommendation: build **MSPDI XML + XER** first, P6 XML second, `.mpp` only via an explicit
conversion step. If the client sends `.mpp`, the product says "export to XML" rather than
silently failing.

### 3.2 Field mapping

| Source | Ours |
|----------------------------|----------------------------------------------|
| Task name / activity name | `Task.title` |
| Outline level, WBS code, summary flag | `wbs_code`, `wbs_parent_id`, `is_summary` (new columns) |
| Duration | `duration_days` **plus** `estimated_hours` derived via a named calendar assumption |
| Start / finish (planned) | `planned_start`, `planned_finish` (new) |
| Baseline start / finish | `baseline_start`, `baseline_finish` (new) |
| Actual start / finish, % complete | `actual_start`, `actual_finish`, `percent_complete` (new) |
| Predecessor links with type + lag | `project_dependencies` rows |
| Milestone (zero duration) | `is_milestone`; also mirrored to the `Milestone` table once it has an API |
| Resource assignments | `Resource` rows + `task_assignments` (defer if scope pressure) |
| Constraint type/date, deadline | `constraint_type`, `constraint_date` (keep raw even if unused by agents) |
| Calendars | Store the source calendar name and working-day pattern; default 8 h/day, Mon–Fri when absent |

**Rule: preserve raw source values alongside the normalised ones.** If a duration is 12
working days and our calendar assumption makes it 96 h, both are stored. Nothing is
"helpfully" converted into something unrecoverable.

### 3.3 Import behaviour (this is where imports usually go wrong)

- `POST /api/projects/{id}/import` (multipart) + `GET /api/projects/{id}/imports` history.
- **Preview before commit**: parse → validation report → explicit commit. The report lists
  tasks, links, unparsed/skipped items, calendar assumptions made, and any cycles found.
- **Idempotent re-import**: every task and link stores `external_uid` from the source. A
  second import of the same file updates in place; a changed file shows a diff (added /
  changed / removed) and requires confirmation before applying deletions.
- **Never delete locally-created rows** on re-import — report them as "exists only in PMO".
- Summary tasks: imported as `is_summary` rows, excluded from effort roll-ups to avoid double
  counting, and excluded from the Monitor's task list (they are containers, not work).
- Import into a non-empty project requires an explicit mode: `merge`, `replace_tasks`, or
  `new_project`.

### 3.4 Effort

Two parsers plus mapping plus preview/commit plus diff-merge is the largest single piece
here. Roughly 5–7 build days for MSPDI XML + XER done properly (including tests against real
export files), plus 1–2 for the import screen.

## 4. Workstream 3 — Monitor and Alert on an imported plan

### 4.1 Deterministic schedule metrics first, LLM second

Add `backend/services/schedule.py` computing, per run, from the DB alone:

- planned vs actual start/finish, **schedule variance** in days per task and per phase
- **% complete** (duration-weighted), and drift vs where the baseline says we should be
- **dependency breaches**: successor started while predecessor is unfinished (respecting
  type and lag), and milestones whose required tasks are incomplete
- **critical path** and **float** (longest-path / CPM over `project_dependencies`)
- **blocked-chain exposure**: how many downstream tasks sit behind a blocked task, and their hours
- **KPI actuals** for the KPIs we can compute from data (SPI-like, % complete vs planned,
  overdue count, blocked count, float consumption)
- **rule evaluation**: each `monitoring_rules.predicate` evaluated against those metrics

The LLM then receives *facts with numbers* rather than a text dump, and is asked for
judgement and prioritisation — not for arithmetic. This is the difference between a monitor
that can be defended to a client's PMO and one that emits plausible prose.

### 4.2 Rule predicates

Pack rules are free text ("FEED package review > 30 days overdue with > 20 open comments").
Keep that text for the LLM, and add an optional machine-checkable `predicate`:

```json
{"all": [
  {"metric": "phase_overdue_days", "phase": 1, "op": ">", "value": 30},
  {"metric": "open_tasks", "phase": 1, "op": ">", "value": 20}
]}
```

Predefined metrics only (no user-authored expressions, no `eval`) so a rule can never become
code execution. Rules without a predicate still reach the LLM as guidance, and are marked
"advisory" in the UI so nobody mistakes them for enforced checks.

KPI `formula_spec` uses the same metric vocabulary, e.g.
`{"fn": "ratio", "of": ["earned_hours", "planned_hours_to_date"]}`.

### 4.3 The closed loop the meeting asked for

After a monitor run:

1. Findings are written as `agent_actions` (as now), each pointing at the task/dependency/risk
   rows it concerns.
2. **Agent-proposed changes are staged, not applied.** A `risk_suggestions` payload
   (new risk, re-score probability/impact, mark realised, close) and
   `dependency_anomalies` (predecessor breach, impossible lag, cycle detected post-edit) are
   surfaced in the Risks and Dependencies tabs with Accept / Reject.
3. Accepting writes the change with `source=agent` and the action id, so every register entry
   has an audit trail back to the run that raised it.
4. KPI actuals are stored per run (`kpi_values` table) so trends are real history, not
   re-derived guesses.

Auto-writing the risk register without human acceptance is deliberately excluded: a register
that silently mutates is unauditable, and the first time it re-scores a client's risk without
them seeing it, trust in the whole product goes.

### 4.4 Alert agent

Alert gains a rule-driven path: any predicate that fires produces a candidate alert with a
severity from the rule, then the LLM writes the narrative and recommended response. Slack/
email dispatch stays as is (`services/alert_channels.py`). Dedupe by (rule, task, day) so a
daily scheduler run does not re-alert the same breach.

### 4.5 Effort

`schedule.py` + metric vocabulary + predicate evaluator + agent prompt changes + suggestion
review UI: roughly 4–6 build days.

## 5. Build order

| Step | Content | Why first |
|-------|--------------------------------------------|-----------------------------------|
| 1 | Alembic + four tables + migrations + backfill | Everything else reads from these; doing it late means rewriting every endpoint twice |
| 2 | CRUD APIs + validation (cycles, refs) + tests | Import and agents both depend on the same validators |
| 3 | Risks / Dependencies / KPIs / Rules tabs, including the map | This is the visible deliverable of point 1; demoable without any importer |
| 4 | `schedule.py` + rule predicates + agent rewiring (works on plan-agent projects too) | Proves point 3 on data we already have, before the import risk |
| 5 | Import: MSPDI XML, preview/commit, diff-merge | Highest unknown; do it against real client files |
| 6 | Import: XER, then P6 XML | Second parser reuses the mapping layer |
| 7 | Suggestion review loop, KPI history, polish | Closes point 3 |

Total: **~3 weeks of build for one experienced developer**, or 3–4 focused sessions for me.
Sequence matters more than the estimate: steps 1–4 make point 3 work on generated plans;
step 5 is the only genuinely unfamiliar work.

## 6. Test plan (definition of done)

- `pytest` green, including new tests for: cycle rejection, cascade deletes (no orphan edges,
  per the existing orphan lesson), migration backfill, predicate evaluation, CPM on a known
  network, and each parser against a fixture file.
- Round trip: import MSPDI fixture → 40+ tasks and links present with types and lags →
  re-import same file → **no duplicates, no changes** → edit one task in the file → re-import
  → exactly one diff shown.
- Agents: run Monitor on an imported project with a deliberately breached predecessor and a
  slipped baseline → expect a specific, number-bearing finding, a staged risk suggestion and
  a fired rule. Run it twice → no duplicate alerts.
- Existing demo untouched: the Highway/J10 and Green Methanol seeds still render, and the
  dashboard health scores are in the same range as before the change.

## 7. Decisions needed

1. **`.mpp` support** — require an XML export, or add a Java/MPXJ converter service? (Affects
   effort and hosting.)
2. **Which real file do we build against first** — do we have one MSP export and one
   Primavera export from the client to test with? Parser work without a real file is guesswork.
3. **Calendars** — one global assumption (8 h/day, Mon–Fri) or per-project calendar, with
   Per-Project the honest answer for EPC?
4. **Summary tasks and resources** — in scope for the first cut, or tasks + links + progress
   only?
5. **Risk register ownership** — confirm the staged-suggestion model (agent proposes, human
   accepts) rather than auto-update.
6. **Do imported plans get a domain pack too** — attach content to an imported plan, or keep
   risk/KPI content strictly project-owned after import?
